## Security Findings

### Alert 1
**File:** `C:\xampp\htdocs\TinyTrack\routes\web.php:65-75`; `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\AdminController.php:86-88,173-201,204-249`
**Category:** BrokenAccessControl
**Severity: HIGH | Confidence: 10/10**
**Problem:** Admin routes have no authentication or role middleware. Anyone can access the user list and appointment data, and update or delete users by ID. The admin login check does not protect these separate routes.
**Evidence:** The routes are declared outside the authenticated group. `usersAdmin()` returns all users, while `update()` and `destroy()` operate on the route-selected user without an authorization check.
**Suggested fix:** Put every admin route behind authentication and an explicit admin-role/policy check; do not rely on an email-address comparison as the role boundary.

### Alert 2
**File:** `C:\xampp\htdocs\TinyTrack\routes\web.php:150-153`; `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\NotificationsController.php:14-16,41-54,80-103,116-123`
**Category:** BrokenAccessControl
**Severity: HIGH | Confidence: 9/10**
**Problem:** Notification routes are public. An unauthenticated caller can read a notification by ID, create notifications for any user, and update or delete any notification. The index also loads all notifications.
**Evidence:** `Route::resource('notifications', ...)` and the separate notification GET route are outside authentication middleware. The controller performs global lookups and accepts a caller-selected `user_id` when creating or updating records.
**Suggested fix:** Restrict global notification management to authorized administrators and scope user-facing reads and changes to the authenticated user. Add authorization checks for each notification.

### Alert 3
**File:** `C:\xampp\htdocs\TinyTrack\routes\web.php:80-82,135-148`; `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\BabyController.php:120-121,136-183,208-215`; `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\GrowthController.php:41-74`
**Category:** BrokenAccessControl
**Severity: HIGH | Confidence: 9/10**
**Problem:** Authentication is required for these baby routes, but ownership is not enforced. Any signed-in user can retrieve another user’s baby record, update or delete that baby, and read or create growth records using another baby’s ID.
**Evidence:** The `/babies/{baby}` route checks only `auth`; `BabyController` does not authorize the bound model before returning, updating, or deleting it. Growth endpoints accept `baby_id` or query by `babyId` without checking the baby’s owner.
**Suggested fix:** Authorize every baby operation with the policy, scope lookups and writes through the authenticated user’s babies relationship, and apply the same ownership check to growth records.

### Alert 4
**File:** `C:\xampp\htdocs\TinyTrack\routes\web.php:168-172`; `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\AppointmentController.php:11-27,39-66`; `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\VaccinationController.php:16-21,74-81`
**Category:** BrokenAccessControl
**Severity: HIGH | Confidence: 10/10**
**Problem:** Appointment and vaccination endpoints are available without authentication. Callers can retrieve appointment or vaccination data by baby ID; they can create appointments for any existing baby and toggle vaccination status. The vaccination ownership checks explicitly skip authorization when the caller is a guest.
**Evidence:** All four routes are outside an auth middleware group. Appointment creation validates only that the baby exists; vaccination checks use `Auth::check() && ...`, allowing unauthenticated requests through.
**Suggested fix:** Require authentication on these routes, then authorize the authenticated user against the baby associated with every read or write.

### Alert 5
**File:** `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\NotificationsController.php:41-54`; `C:\xampp\htdocs\TinyTrack\resources\views\user\mybaby.blade.php:862-863,1817-1860`
**Category:** StringInjection
**Severity: HIGH | Confidence: 9/10**
**Problem:** Stored notification content can execute as JavaScript in a recipient’s session. The Blade view initially escapes title and message, but the click handler reads them as text and interpolates them into an HTML template that is inserted with `insertAdjacentHTML`. Public notification creation lets an attacker target a user with crafted content.
**Evidence:** The controller accepts caller-supplied title/message and user ID; the modal inserts those values into HTML without escaping or sanitizing them.
**Suggested fix:** Insert notification text using safe DOM text APIs, or apply context-appropriate sanitization before rendering. Restrict notification creation and recipient selection to authorized callers.

### Alert 6
**File:** `C:\xampp\htdocs\TinyTrack\app\Http\Controllers\BabyController.php:52-64,136-158`; `C:\xampp\htdocs\TinyTrack\app\Models\Baby.php:25-30`; `C:\xampp\htdocs\TinyTrack\config\filesystems.php:41-47,76-78`; `C:\xampp\htdocs\TinyTrack\public\.htaccess:22-32`
**Category:** DataIntegrityFailure
**Severity: HIGH | Confidence: 8/10**
**Problem:** Baby-photo uploads have no server-side file-type validation and are stored on the public disk. The configured public storage link and web-server rules make uploaded files directly reachable; an HTML upload can therefore be served from the application’s origin. A victim who opens the returned photo URL can execute attacker-controlled JavaScript in that origin.
**Evidence:** `baby_photo` is omitted from the validation rules, then stored directly on the public disk. The model exposes a photo URL, and the repository contains the public storage link.
**Suggested fix:** Enforce server-side image-only validation and verify content, store uploads outside the web root where possible, and serve user content from a separate origin or as a non-executable download.
